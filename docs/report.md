## 1. Введение

В рамках практической работы была разработана CLI-утилита **Docs Translator CLI**. Цель проекта — создать консольный инструмент для перевода текстовых файлов документации и отдельных строк с использованием внешнего REST API переводчика, а также локального хранения истории переводов и пользовательского глоссария терминов.

Работа выполнялась в два независимых потока разработки:

1. версия проекта, созданная с помощью **ChatGPT**;
2. версия проекта, созданная с помощью **Claude**.

Обеим нейросетям было передано одно и то же заранее подготовленное техническое задание в формате Markdown. После получения архивов проектов была выполнена проверка установки, структуры, команд CLI, REST-интеграции, unit-тестов, покрытия, качества кода через `ruff`, документации и соответствия требованиям преподавателя.

Главная цель сравнения — оценить, насколько разные ИИ-инструменты способны реализовать один и тот же проект по формализованному техническому заданию, какие ошибки возникают в процессе разработки, как они исправляются и какая версия лучше подходит для дальнейшей публикации на GitHub.

## 3. Описание проекта Docs Translator CLI

**Docs Translator CLI** — это консольная Python-утилита для перевода текстовой документации через внешний REST API переводчика.

Основные возможности:

- перевод отдельных текстовых строк;
- перевод файлов документации `.txt`, `.md`, `.rst`;
- определение языка текста;
- получение списка поддерживаемых языков;
- управление пользовательским глоссарием терминов;
- применение терминов глоссария перед переводом;
- сохранение истории переводов в SQLite;
- просмотр истории переводов;
- экспорт истории в JSON, CSV и Markdown;
- настройка API URL, API key, языков по умолчанию и timeout;
- диагностика окружения и доступности REST API;
- логирование работы приложения.

Для REST-интеграции выбран **LibreTranslate-compatible API**. Во время проверки выяснилось, что публичный LibreTranslate API может требовать оплату или API-ключ. Поэтому для тестирования был использован локально поднятый экземпляр LibreTranslate по адресу:

```text
http://localhost:5000
```

Такой подход сохраняет выполнение обязательного требования REST API, но не привязывает проверку к платному внешнему ключу.

## 5. Реализованные CLI-команды

Всего реализовано 12 команд. Это превышает минимальное требование преподавателя в 7 команд или подкоманд.

| № | Команда | Назначение | REST API |
|---:|---|---|---|
| 1 | `translate-text` | Перевод отдельной строки. | `POST /translate` |
| 2 | `translate-file` | Перевод текстового файла документации. | `POST /translate` |
| 3 | `detect-language` | Определение языка текста. | `POST /detect` |
| 4 | `languages-list` | Получение списка поддерживаемых языков. | `GET /languages` |
| 5 | `glossary-add` | Добавление термина в локальный глоссарий. | Не использует API |
| 6 | `glossary-list` | Просмотр терминов глоссария. | Не использует API |
| 7 | `glossary-remove` | Удаление термина из глоссария. | Не использует API |
| 8 | `history-list` | Просмотр истории переводов. | Не использует API |
| 9 | `export-history` | Экспорт истории переводов. | Не использует API |
| 10 | `config-set` | Запись настройки в config-файл. | Не использует API |
| 11 | `config-show` | Просмотр эффективной конфигурации. | Не использует API |
| 12 | `doctor` | Диагностика окружения и API. | `GET /health`, fallback `GET /languages` |

## 6. Соответствие команд REST API

### 6.1. REST-команды

| Команда | Метод и endpoint | Тело/параметры запроса | Ожидаемый ответ | Локальное действие |
|---|---|---|---|---|
| `translate-text "Hello" --source en --target ru` | `POST /translate` | `q`, `source`, `target`, `format`, `api_key` при наличии | `translatedText` | Применяет глоссарий, сохраняет запись в историю. |
| `translate-file README.md --source en --target ru` | `POST /translate` | Сегменты файла в `q`, языки, формат, ключ при наличии | `translatedText` строкой или списком | Создаёт переведённый файл, сохраняет историю. |
| `detect-language "Привет"` | `POST /detect` | `q`, `api_key` при наличии | список языков с `confidence` | Выводит наиболее вероятный язык. |
| `languages-list` | `GET /languages` | без обязательных параметров | список языков и target-языков | Выводит таблицу языков. |
| `doctor` | `GET /health`, fallback `GET /languages` | без обязательных параметров | статус API или список языков | Проверяет config, DB, log file и API. |

### 6.2. Локальные команды

| Команда | Используемое хранилище | Результат |
|---|---|---|
| `glossary-add` | SQLite | Добавляет термин, языковую пару, флаг case-sensitive и заметку. |
| `glossary-list` | SQLite | Показывает таблицу терминов. |
| `glossary-remove` | SQLite | Удаляет термин по исходному тексту и языковой паре. |
| `history-list` | SQLite | Показывает предыдущие переводы. |
| `export-history` | SQLite + файловая система | Создаёт JSON/CSV/Markdown-файл с историей. |
| `config-set` | JSON config | Сохраняет настройку. |
| `config-show` | JSON config + env + defaults | Показывает итоговую конфигурацию. |

## 8. Конфигурация, логирование и хранение данных

### 8.1. Конфигурация

Поддерживаются следующие способы настройки:

1. CLI-опции;
2. переменные окружения;
3. JSON config-файл;
4. значения по умолчанию.

Основные настройки:

| Настройка | Назначение |
|---|---|
| `base_url` | Базовый URL LibreTranslate-compatible API. |
| `api_key` | API-ключ переводчика, если API его требует. |
| `default_source` | Язык исходного текста по умолчанию. |
| `default_target` | Целевой язык по умолчанию. |
| `timeout` | Timeout HTTP-запросов. |
| `db_path` | Путь к SQLite-хранилищу. |
| `config_path` | Путь к JSON config-файлу. |
| `log_level` | Уровень логирования. |

### 8.2. Локальное хранение

В SQLite хранятся:

- пользовательский глоссарий;
- история переводов;
- служебная таблица миграций схемы.

API-ключи не должны сохраняться в SQLite. История переводов хранит текстовые фрагменты, языки, provider, base URL, пути файлов, технические метаданные и сведения о применённых терминах.

### 8.3. Логирование

Логирование реализовано через стандартный модуль `logging`. Логи пишутся в файл в системном каталоге пользователя, путь рассчитывается через `platformdirs`. В README Claude-версии дополнительно указано, что используется ротируемый файл логов и API key не должен попадать в лог.

## 9. Обработка ошибок

В обеих версиях реализована обработка основных категорий ошибок:

| Категория ошибки | Ожидаемое поведение CLI |
|---|---|
| Недоступен REST API | Понятное сообщение об ошибке, ненулевой exit code. |
| Timeout HTTP-запроса | Сообщение о сетевой ошибке или timeout. |
| Неверный API key | Сообщение об ошибке авторизации. |
| Rate limit | Сообщение о превышении лимита. |
| Ошибка сервера API | Сообщение о серверной ошибке. |
| Неверные параметры CLI | Ошибка валидации Typer. |
| Отсутствует входной файл | Ошибка файловой системы. |
| Выходной файл уже существует | Отказ от перезаписи без `--overwrite`. |
| Дубликат термина в глоссарии | Сообщение о конфликте или замена через `--replace`. |
| Некорректный JSON config | Сообщение о проблеме конфигурации. |

При ручной проверке была подтверждена корректная обработка случая, когда файл экспорта уже существует:

```bash
uv run docstrans export-history history.json --format json
```

Результат:

```text
Error: output file already exists: history.json
```

или в Claude-версии:

```text
Error: Output file exists, use --overwrite: history.json
```

```text
SIM105 Use contextlib.suppress(Exception) instead of try-except-pass
src/docstrans/cli.py:53:9
```

Проблемный фрагмент:

```python
try:
    self.close()
except Exception:
    pass
```

Исправление:

```python
from contextlib import suppress

with suppress(Exception):
    self.close()
```

## 16. Главные практические выводы

1. Подробное ТЗ оказалось ключевым фактором успеха. Обе нейросети смогли реализовать проект потому, что задача была заранее формализована: команды, REST endpoints, структура, тесты, конфигурация и логирование были описаны явно.

2. Нельзя доверять заявлениям нейросети о прохождении тестов без локальной проверки. ChatGPT указал, что `ruff` и тесты прошли, но первый архив не собирался через `uv sync`, а позднее был найден один lint-дефект.

3. `uv` удобен для воспроизводимой проверки проекта. Команды `uv sync`, `uv run pytest`, `uv run ruff check .` и `uv run docstrans ...` позволяют быстро понять, действительно ли архив рабочий.

4. REST API — самая рискованная внешняя зависимость. Публичный LibreTranslate может требовать ключ или оплату, поэтому локальный LibreTranslate оказался практичным решением для демонстрации и тестирования.

5. Unit-тесты обязательно должны мокировать REST API. Обе версии используют тесты без реальных HTTP-запросов, что делает тестирование стабильным.

6. Форматирование Markdown при машинном переводе — отдельная сложная проблема. Даже если команда `translate-file` работает, качество сохранения Markdown-разметки требует дополнительных тестов на реальных документах.

7. Для GitHub-публикации нужно очищать архивы от мусора: `.pytest_cache`, `.ruff_cache`, `__pycache__`, случайные директории вроде `{src`, локальные DB и реальные `.env` файлы.

## 17. Рекомендации по промпт-инжинирингу

1. Перед генерацией кода нужно сначала сделать подробное ТЗ. Формулировка «сделай CLI» недостаточна; нужны команды, аргументы, API, структура, тесты, ошибки и критерии приёмки.

2. В промпте нужно явно требовать не только код, но и проверку:

```text
Перед выдачей архива обязательно выполни:
uv sync
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run docstrans --help
```

3. Нужно требовать, чтобы нейросеть не включала в архив служебные файлы:

```text
Не включай в архив .venv, __pycache__, .pytest_cache, .ruff_cache, локальные DB, .env с секретами.
```

4. После первой генерации нужно давать нейросети реальные логи ошибок, а не пересказывать проблему своими словами. На примере ChatGPT это сработало: после передачи `run_log.md` packaging был исправлен.

5. Для проверки REST API нужно заранее определить режим демонстрации: внешний ключ или локальный сервер. В данном проекте надёжнее использовать локальный LibreTranslate.

Практическая работа выполнена. Были получены две рабочие реализации CLI-утилиты **Docs Translator CLI**, созданные разными ИИ-инструментами — ChatGPT и Claude. Обе версии используют REST API, имеют более 7 команд, локальное SQLite-хранилище, глоссарий, историю переводов, экспорт, конфигурацию, логирование, README и unit-тесты.

По итогам проверки:

- **ChatGPT** лучше показал себя по покрытию тестами и подробности API-документации, но потребовал исправления packaging и одного ruff-дефекта.
- **Claude** лучше показал себя по количеству тестов, чистоте lint-результата и подробности CLI help, но создал лишний мусорный каталог `{src` и имеет меньшее покрытие.
- Оба инструмента справились с задачей, но оба результата требовали человеческой проверки.
- Основной фактор успеха — заранее составленное подробное ТЗ.
- Для реального использования проекта главным дальнейшим улучшением будет подключение более качественного переводчика и усиление защиты Markdown-разметки.

Итоговый вывод: для разработки CLI-утилит с чётким техническим заданием оба ИИ-инструмента применимы, но результат нельзя принимать без проверки через `uv sync`, `pytest`, `ruff`, ручной запуск CLI-команд и анализ структуры архива.
